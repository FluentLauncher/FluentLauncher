# 插件市场与宿主接口方案

日期：2026-11-13

状态：待审核；本文描述目标设计，尚未修改应用、SDK 或发布目录。

## 目标与实施边界

将设置中的“插件”重构为“插件市场”，让用户先看懂插件用途，再安装、使用和管理。安装过程、结果和失败恢复必须在用户操作的位置可见。保持 Windows 11 / MyGo 原生 UI、现有主题与独立插件仓库，不引入 WebView。

接口层先形成可落地的宿主服务契约，补上双向通信与能力协商，再按实际用途开放服务。稳定扩展点能让多数新插件只发布插件包，但新增操作系统能力、宿主绘制组件或协议语义仍可能需要升级主程序，不能承诺以后完全不用改宿主。

本次依据 `AGENTS.md` 中“涉及重大架构、数据模型、权限边界变更时，先给出方案供审核”的约定，先提交设计和接口规划。以下 TODO 是后续实现的验收清单，不代表已经实现。

## 市场页面

### 信息架构

- 侧栏和标题统一改为“插件市场”。页面内有“发现插件”“已安装”“可更新”三个视图，数量来自本地合并模型。
- 顶部工具栏提供插件搜索、紧凑的“刷新”按钮、“本地安装”菜单。搜索只过滤已加载的元数据，不扫描目录、不启动插件。
- “本地安装”展开“从 ZIP 安装”“从目录安装”“打开插件目录”。首次进入后台读取已验证缓存，再刷新目录；不用要求用户先点一次刷新。
- 首次进入默认“发现插件”，同一设置窗口内保留用户选择的视图。安装后保留当前视图、搜索和滚动位置。
- “发现插件”展示全部可浏览条目，包括已安装插件；安装成功不把条目从市场中移除。
- “已安装”合并官方与第三方本地插件；第三方没有在线条目时仍能管理。
- 目录失败显示“当前显示缓存目录”与重试入口。没有可信下载信息时允许浏览回退介绍，安装按钮明确不可用；不伪造最新版本。

### 插件条目

默认宽窗口采用双列条目，窄窗口降为单列，避免原先“卡片里再嵌一大张表单”的层级。最终断点以设置窗口实际可用宽度为准，用 `ui.NewTester` 检查。

每个条目只展示：

1. 约 48 DIP 图标、插件名称、作者与官方来源。
2. 最多两行简短介绍；点击名称或“详情”查看完整说明。
3. 当前可安装版本，以及“已安装 / 可更新 / 安装中 / 安装失败”等安装状态。
4. 对应的紧凑操作：“安装”“更新”“使用”“管理”。安装动作不会铺满整行。

发现页以功能为主。进程号、启动耗时、查询耗时、stderr、重启按钮移至插件详情的“运行诊断”折叠区。运行状态与安装状态分开：“已启用，按需启动”不能误显示成安装失败。

不增加缺少数据来源的评分、下载量、榜单或“热门推荐”。四款插件时无需额外分类栏；分类元数据存在且数量增长后，再决定是否显示筛选。

### 插件详情与管理

详情在当前内容区打开，提供返回入口，保留列表位置。包含：

- 图标、名称、作者、版本、安装 / 更新 / 使用操作。
- 简介、使用示例、触发词、插件声明的命令。
- 完整介绍、版本说明、可选静态截图，以及源码 / 主页链接。
- 宿主最低要求与所需服务；不兼容时解释原因，并链接主程序更新入口。
- 已安装时展示启用开关、“参与普通搜索”、配置、快捷键、卸载。
- “运行诊断”折叠区展示现有状态、耗时、错误、stderr 和重启；“包信息”展示 ID、安装路径与来源。

插件设置优先由声明式字段生成原生控件。复杂交互继续放在插件自己的窗口，不把插件 UI 代码嵌入宿主设置窗口。

## 安装反馈与状态

### 状态机

```text
未安装 / 可更新
  → 下载中（已下载字节 / 总字节，可取消）
  → 校验中（不显示编造的百分比，可取消）
  → 安装中（替换与运行时重配置，进入提交阶段后不可取消）
  → 已安装 / 已更新
       或
     失败（原因、重试；保留此前可用版本）
```

- 当前插件的按钮原位显示阶段和忙碌状态，其他条目仍可浏览。首版保持单个安装事务，其他安装入口禁用并说明“另一个插件正在安装”；暂不增加并发安装与后台队列。
- 成功时在页面操作区显示明显反馈，例如“剪贴板历史已安装并启用”，并提供“立即使用”“配置快捷键”；条目同时切换为已安装状态。成功通知可以关闭，条目状态持续保留，避免只靠短暂 Toast。
- 失败信息在对应条目与详情中保留，附“重试”，不与自动保存状态共用一条易被覆盖的灰字。未执行安装的插件不应显示错误。
- 本地 ZIP 与目录安装同样产生结果提示；包检查失败与包替换失败区分显示。
- 新安装默认启用；更新保持原先启用状态、触发词设置、命令 ID 和用户快捷键，不把原本禁用的插件自动打开。
- “安装完成”表示包替换、运行时注册与配置保存成功，不表示插件的每个业务功能已经实机验证。配置保存失败要明确提示，不能提前宣称“已安装并启用”。
- 更新先下载并校验，再暂停相关进程并替换。失败回滚包与运行时注册；其他插件继续工作。沿用并扩展 `ReplacePackage`，不在每个 UI 回调中重新实现替换逻辑。
- 反馈状态属于 App 的安装模型；关掉设置窗口不丢失后台安装结果。UI 状态通过 `Window.Update` / 现有发布入口更新，不在工作 goroutine 直接写视图数据。

建议状态拆分为 `CatalogState`、`PackageOperation`、`PluginFeedback`。`PackageOperation` 保存插件 ID、目标版本、阶段、已下载字节、总字节与取消句柄；插件列表由目录与本地注册快照按稳定 ID 合并，不能再按显示名称选择插件。

## 图标、介绍与元数据

### Manifest 可选字段

现有基础字段继续有效，新增字段可缺省：

```json
{
  "icon": "assets/icon.png",
  "author": "FluentLauncher",
  "homepage": "https://github.com/FluentLauncher/FluentLauncher-plugins",
  "description": "简短介绍，保留现有字段",
  "readme": "README.md",
  "minHostVersion": "0.1.0",
  "requiredHostServices": [],
  "settings": []
}
```

示例最低版本仅展示格式，实施时按首个实际提供对应能力的发布版本填写。

- 图标推荐透明 PNG，至少 128×128，推荐 256×256；展示时按 DPI 解码，禁止 UI 线程读文件。
- 图标、readme 与本地截图必须是包内相对路径，验证最终解析结果及解包路径，不能越出插件目录。限制单图文件大小和解码像素数。
- 先支持 PNG，避免为图标再引入可执行 HTML 或任意 SVG 渲染。缺少图标时使用现有线性图标体系的通用插件图标。
- 四款官方插件在插件仓库内各自携带图标与使用说明，不把主程序写死为四个插件 ID 的映射表。
- README 只渲染受限文本 / Markdown 子集，禁用 HTML、脚本、远程自动加载和主动内容。
- 搜索结果的可选 `icon` 是独立字段：首版只引用包内图标或已协商的资源引用，缺省回退插件图标，不接受任意网络地址。

### 签名目录的展示字段

目录条目增加可选 `author`、`icon`、三语 `description`、`usage`、`releaseNotes`、`homepage`、`sourceUrl`、`minHostVersion`、`requiredHostServices`；截图作为可选资源集合。名称与摘要继续使用现有三语映射和回退策略。

安装前就要显示图标，因此目录图标不能只放在尚未下载的 ZIP 中。发布工具将同一张源图分别放入插件 ZIP 与固定 Release 资源，签名目录记录资源的固定 URL、SHA-256 和大小。主程序异步下载、校验、按哈希缓存；离线使用缓存，失败回退通用图标。目录与本地包内容以稳定 ID 和包版本关联。

新增展示字段保持目录 schema 1 的可选扩展，旧宿主忽略未知字段。新增宿主能力若被插件强制依赖，旧宿主无法读取新约束时，必须通过新的目录 schema 发布边界或插件明确的初始化拒绝阻止运行，不能仅依赖旧宿主会忽略的 `minHostVersion`。发布前按旧版本宿主进行兼容测试，再确定具体切换版本；不能只在新 UI 中禁用按钮就声称旧宿主安全兼容。

| 复制文本、打开链接、打开路径 | 结果 action kinds | 保留，避免同类接口语义冲突 |

## 建议开放的宿主服务

“首批”指审核通过后实现的通用接口；“后续”仅规划语义，不以空实现宣称已支持。

| 优先级 | 服务名（草案） | 实际用途与边界 |
| --- | --- | --- |
| 首批 | `ui.notify` | 统一成功、信息、错误反馈；前台用宿主提示，后台按用户通知偏好；带插件来源、替换 ID，避免重复刷屏 |
| 首批 | `launcher.show` / `launcher.hide` | 插件触发宿主搜索、填入查询、归还焦点；不让插件直接改 App 字段 |
| 首批 | `clipboard.readText` / `clipboard.writeText` | 翻译、文本工具与复制结果共用；写入沿用已有动作语义，读取必须明确声明 |
| 首批 | `dialogs.open` / `dialogs.save` | 原生文件 / 目录选择；明确取消结果与父窗口关系，用户取消不是插件错误 |
| 首批 | `settings.get` / `settings.set` | 只访问当前插件配置；依据 Manifest 声明生成原生输入、开关、选择、数字控件，并发送配置变更通知 |
| 首批 | `context.get` | 宿主版本、语言、平台、当前插件的数据目录 / 缓存目录；不暴露任意宿主环境变量 |
| 首批 | `shell.open` / `shell.reveal` | 统一打开链接、路径或定位文件；带参数的进程启动、提权另行定义，不拼接 shell 字符串 |
| 后续 | `tasks.report` / `tasks.complete` | 下载、转换、截图保存等异步任务的进度与最终结果；任务 ID 带进程会话，旧进程不能覆盖新进程任务 |
| 后续 | `resources.register` / `preview.show` | 包内 / 插件临时目录的图片、Markdown 预览及结果图标；只传资源引用，不把大图 Base64 塞进 4 MiB 帧 |
| 后续 | `clipboard.readImage` / `clipboard.writeImage` | 图片处理与 OCR 插件复用；通过资源引用传输，受清理与大小限制 |
| 后续 | `context.selection` / `context.foreground` | 用户主动调用命令时的选中文本、当前窗口上下文；按操作获取，避免每次搜索都抓取 |
| 后续 | `events.subscribe` / `events.unsubscribe` | 主题 / 语言 / 插件配置等白名单事件；退订、禁用、崩溃时清理，只向已运行进程推送 |
| 有具体需求再做 | `windows.*`、`system.volume.*`、`search.query` | 窗口操作、音量、搜索宿主结果；明确去重、递归、焦点和性能限制后再开放 |

持久数据不需要先做万能 KV / 文件系统代理：为插件提供稳定 `dataDir`、`cacheDir`，插件按自己的数据模型保存。插件自行进行普通 HTTP 请求与业务计算；不为“统一接口”增加一个全能网络代理、任意代码执行入口或主数据库读写接口。

插件配置首版不提供“密码字段即安全存储”的承诺。凭据若确有需求，另接 Windows Credential Manager 或等效系统凭据服务；不把密钥当普通 JSON 配置。

## 通信与能力协商

### 先改变读循环，再增加方法

保留四字节长度帧与 JSON-RPC 2.0，协议版本仍为 1；通过可选能力进行扩展。实现前必须用现有 SDK 及旧宿主回归验证，而非仅凭字段可选就推断兼容。

```text
宿主调用方 ── pending host:<id> ──┐
                                ├── 写锁 ── stdio ── 插件
宿主服务响应 ────────────────────┘

插件 stdout ── 唯一读循环 ──┬── response：按 ID 唤醒 pending
                           ├── host.* request：分派宿主服务
                           └── notification：分派白名单事件 / 状态
```

- 每个进程会话仅一个 reader；宿主和 SDK 两端都要支持请求 / 响应分类，不能多个 goroutine 抢读 stdout / stdin。
- 请求 ID 区分方向（新实现可用 `h:1`、`p:1`），响应原样回传，不限制所有请求必须是整数。
- 保留现有查询去重、取消和动作优先级；宿主服务响应不等待当前查询的 operation gate，否则插件在 `query` / `execute` 内调用宿主会死锁。
- pending 表和服务并发必须有界；超时、取消、进程退出时结束等待并清理。旧进程的回调不能作用于新安装的进程会话。
- 需要 UI 的调用交给 App 层调度。UI 构建不等待插件；需要用户交互的服务使用独立的超时策略，不能套用搜索查询毫秒级超时。
- UI 交互服务不得从每次 `query` 中弹窗或抢焦点；`query` 内只允许声明的无交互读取。执行命令 / 结果动作时发放当前调用上下文，交互服务检查此上下文。
- 用户关掉窗口、禁用、卸载或升级插件时，清理它的挂起服务、对话框、任务和事件订阅。

### 协商步骤

1. 继续现有 `initialize` 请求与版本 / ID 校验。
2. 新 SDK 的插件在现有 `capabilities` 数组中可选声明 `hostServices.v1`；未声明的旧插件不收到新方法。
3. 新宿主仅向声明该能力的插件发送 `configureHost`，内容为宿主版本、语言、插件专属目录、支持的服务与各服务版本。
4. 插件完成配置后才可调用 `host.*`。旧宿主不发送 `configureHost` 时，新插件可用旧业务路径降级；强依赖的插件明确报告“需要升级主程序”，不静默失败。
5. Manifest 的 `requiredHostServices` 用于安装前兼容判断；运行时以实际协商结果为准。可选服务缺失走降级，必须服务缺失则拒绝启用并解释缺少什么。

服务注册表以 `name + version + handler` 为单位，版本描述行为，不用 Go 类型名做协议。新增一个可选方法不升级整个协议；删除或改变既有服务语义时升级该服务主版本。

### RPC 示例

```json
{
  "jsonrpc": "2.0",
  "id": "p:12",
  "method": "host.ui.notify",
  "params": {
    "kind": "success",
    "title": "截图已保存",
    "message": "图片已保存到所选目录",
    "replaceId": "capture-save"
  }
}
```

宿主根据当前连接绑定插件身份，不接受参数中的 `pluginId` 作为身份依据。成功返回 `{"jsonrpc":"2.0","id":"p:12","result":{}}`。未知方法用标准 `-32601`；参数错误用 `-32602`；宿主业务错误统一带稳定的 `data.kind`（如 `unsupported`、`not_declared`、`cancelled`、`unavailable`），SDK 依据代码处理，界面展示本地化说明。

### SDK 形态

```go
// 草案，不是当前已发布 API。
type Host interface {
    Supports(service string, version int) bool
    Call(ctx context.Context, method string, params any, result any) error
}

// 原 Handler 的 Query / Execute 保持不变。
type HostAware interface {
    SetHost(Host)
}
```

`Call` 只调用已注册且已协商的宿主服务，不是任意反射执行入口。SDK 再封装 `Notify`、`ReadText`、`ShowQuery` 等类型明确的方法。SDK 继续只依赖 Go 标准库；不泄漏 MyGo 的 Context、Window、Element、Windows handle 或宿主内部结构。

## 权限与可信模型

继续以“受信任的本地可执行插件”为前提。宿主服务的声明 / 调用校验用于说明数据访问、限制宿主代理接口和避免误用，不能阻止 EXE 自己访问系统，因此不能宣传为系统沙箱。

- 现有 `permissions` 字段的历史语义须核对发布插件；新增服务使用明确的服务声明，并单独标识会读取剪贴板、选区等数据的访问。
- 已有安装授权不等于给每次 API 弹确认窗。按安装和配置时的选择执行，仅在新增数据访问、提权或覆盖用户数据等有意义的操作上提供相应交互。
- 市场详情展示服务用途；更新新增敏感访问声明时展示变化，不把普通新增描述字段也变成审批。
- 常规服务只作用于调用插件自己的配置、目录和任务。其他插件配置、宿主主数据库、快捷键总表不提供直接写入。
